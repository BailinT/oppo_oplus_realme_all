## 四、同步流程（上游有更新时）

### 场景 A：cctv18 改了某个子版本的构建脚本（最常见）

**表现**：cctv18 三仓出现新 commit，如 "Improve robustness of patch commands"、"Update 6.12.68 GKI compiling scripts"。

**处理**：
1. 看 diff：`gh api repos/cctv18/oppo_oplus_realme_sm8850/commits/<sha> --jq '.files[] | "\(.status) \(.filename)"'`
2. 如果是**新增子版本**（如 `fastbuild_6.12.69_gki.yml`）→ 把该 workflow 复制进本仓，施加 hwid 改造（如果做 hwid 版），触发验证
3. 如果是**现有 workflow 的修复**（如 patch 命令健壮性）→ 手动对照移植到本仓对应 workflow（注意保留本仓的署名与 AnyKernel3 硬规则）
4. 验证构建后提交，更新本文档的「上游动态」

### 场景 B：OnePlusOSS 新增分支（新机型/新子版本）

1. 查分支列表（见上方命令）
2. 抓 Makefile 确认 SUBLEVEL：`curl -s https://raw.githubusercontent.com/OnePlusOSS/<repo>/<branch>/Makefile | grep -E '^(VERSION|PATCHLEVEL|SUBLEVEL) ='`
3. 参照同芯片现有 workflow 复制改造（env 块改 SUB_VERSION/源码 URL；天玑树保留 vendor-fix 步骤）
4. 触发验证 → 绿后更新本文档表格

### 场景 C：SUSFS / KPN 等外部依赖更新

一般**不需要**动 workflow（都是 `latest` 动态拉取）。只有出现构建失败且错误指向这些组件时才需要处理。
